# PayOps Phase 2: Client API (plan for approval)

Repo: github.com/sngwane/payops (`main` @ 2b54c92). Delivered as one PR. Nothing is built until you approve.

## 1. Goal
A .NET 10 Client API that the future UI and the other APIs use to manage the client hierarchy:
`PrimaryClient` 1..n `SecondaryClient`. Every batch belongs to a secondary client. It also manages the client data the
legacy system kept next to clients: access keys and the client's own bank accounts.

## 2. Decisions needed (my recommendation first)
| # | Question | Recommended | Alternative |
|---|---|---|---|
| 1 | Scope of this phase | Core clients + **API keys** + **bank accounts** | Core clients only (keys and accounts in a later phase) |
| 2 | Sign-in for the API | **Entra ID** (JWT bearer, roles `PayOps.ClientAdmin` = read/write and `PayOps.Reader` = read-only). It is only switched off in the `Development` environment until you register the app in Entra | No auth yet, added later |
| 3 | Who sets `UniqueClientId` | **Entered by the admin** (legacy IDs are kept as-is), unique, can't change after creation | Generated by the API |
| 4 | Who owns bank accounts (Nominated / Charges) | **Primary client** (legacy links them through `PrimaryClientBankAccountType`) | Secondary client |
| 5 | Deactivating a primary that still has active secondaries | **Block** it (HTTP 409); deactivate the secondaries first | Deactivate all its secondaries automatically |
| 6 | Moving a secondary to another primary | **Only for placeholder secondaries** (`RequiresReview = 1`, see 4.4) | Allowed for any secondary |

Technical defaults (tell me if you want any changed):
- **Minimal APIs** (.NET 10 built-in validation + OpenAPI document), grouped per resource. Alternative: MVC controllers.
- **API key hashing: SHA-256.** Keys are 256-bit random values shown once, and the hash is fast enough to check on every request. Slow hashes (PBKDF2/Argon2) only help for low-entropy passwords.
- Errors are returned as **ProblemDetails** (RFC 9457). Lists are paged (`page`, `pageSize` default 50, max 200).
- Optimistic concurrency uses a `RowVersion` column. Updates send `rowVersion` back, and a stale value gets HTTP 409.
- Hard deletes aren't possible. Records are deactivated (`IsActive = 0`) or, for keys, revoked.

## 3. Solution layout (follows the Payments pattern)
```
src/Services/Client/PayOps.Client.Data   ClientDbContext (maps only the client tables) + LINQ queries/commands, DTOs, key hasher
src/Services/Client/PayOps.Client.Api    ASP.NET Core minimal API: endpoints, auth, OpenAPI, ProblemDetails, /health, Dockerfile
tests/PayOps.Tests                       + Client data tests and API tests (WebApplicationFactory + the existing Testcontainers fixture)
```
- `ClientDbContext` reuses the shared `IEntityTypeConfiguration`s (`PrimaryClient`, `SecondaryClient`, `ClientApiKey`,
  `ClientBankAccount`, `AccountType`) exactly like `PaymentsDbContext`. Only `PayOpsDbContext` owns migrations.
- The connection string comes from configuration `ConnectionStrings:PayOps` (user-secrets / environment variable). It is never committed.
- CI needs no change: the existing workflow builds and tests the whole solution.

### 4.4 Orphan legacy batches (your decision today: placeholders, flagged for review)
The Client API only provides the schema and the tools. The rows themselves are created later, in the legacy data-migration phase:
- The ETL creates one inactive placeholder primary, `LEGACY-UNMATCHED`. Each of the 11 unmatched legacy `UniqueClientId`s
  becomes a secondary under it with `RequiresReview = 1` and the name taken from the legacy batch. No payment history is lost.
- In the Client API, `GET /api/secondary-clients?requiresReview=true` lists them, and
  `POST /api/secondary-clients/{id}/reassign` moves one to a real primary and clears the flag.

## 6. Business rules enforced
- `UniqueClientId`: required, max 20 characters, no spaces, immutable. It must be unique across primaries **and** secondaries, so a key or batch lookup is never ambiguous (the API checks both tables).
- Name: required, trimmed, max 100 characters.
- A secondary can't be created under, or reassigned to, an inactive primary.
- Deactivating a secondary leaves its existing batches untouched. The Batch File API will later refuse new uploads from it.
- API keys: at most 2 active keys per client, so a key can be rotated without downtime. Keys of inactive clients are rejected by the shared `ValidateApiKeyAsync` query. That query sits in `PayOps.Client.Data` so the Batch File API / CoreWCF facade can reuse it.
- Bank accounts: branch code and account number are digits only.

## 7. Tests (xUnit + Testcontainers SQL Server 2022, existing fixture)
- Schema: the new tables, `CK_ClientApiKey_Owner`, the filtered unique index and the RowVersion columns exist.
- Data: create/update/list/paging/search, cross-table UniqueClientId uniqueness, concurrency conflict, deactivate-primary block, reassign only for RequiresReview.
- API keys: the full key is shown once, only the hash is stored, validate accepts active keys and rejects revoked/expired/inactive-client keys, max 2 active.
- API: each endpoint via WebApplicationFactory, including 400/404/409 ProblemDetails, and 401/403 with auth on (Reader can't write).
- Checks: `dotnet build` (warnings as errors), `has-pending-model-changes` clean, the idempotent script runs twice cleanly.
